# AM2ARM 1.6.3 Linux runtime

The launcher ships 167 ARM64 ELF files. The Standard edition patch carries 23 more and Dual Screen carries 24. These include the edition-specific game executables. The installer reconstructs the game with the player's original AM2R 1.1 Windows ZIP. The firmware supplies the physical display, audio and input drivers.

[inventory.tsv](inventory.tsv) lists each shipped ELF by location, architecture, byte count, SHA-256, provider and direct ELF library requirements. A `launcher` path starts at the managed `AM2ARM/` directory. A `standard` or `dual` path starts at the installed edition directory and identifies bytes carried inside that edition's `wrapper.bin`. Repeated paths in the two editions are intentional. `sha256_before_packaging_strip` identifies the original Debian file or unstripped build output where available. A dash means that only the final binary hash is recorded. ELF type `DYN` covers shared libraries and position-independent executables. Libraries loaded with `dlopen` or passed by a launcher argument do not appear in the ELF requirements column.

[debian.tsv](debian.tsv) identifies the 60 Debian 12 binary packages with the exact version, source package, upstream source link, original package SHA-256, purpose and packaged copyright file. The notice path starts at `AM2ARM/`. 186 paths match the original Debian 12 package members byte-for-byte. The three copies of `xkbcomp` match the original Debian binary after `llvm-strip --strip-unneeded`. Each archived package was checked against the Debian 12 ARM64 Packages index, SHA-256 `2ddb1737692e8c45c53e8d57c0ce4cd21c78c5703b830c3226b1423566a06c00`, authenticated by the Debian archive and stable-release keys.

The dArkOS audio bundle adds eight ARM64 files from three Debian 13 packages. Its embedded `AM2ARM/runtime/darkos-audio/SOURCES.txt` identifies the exact packages and hashes. Original PulseAudio and ORC source archives, Debian changes, signatures where supplied, and checksums accompany the launcher source. [dArkOS audio sources](https://github.com/PatchDev-AM2ARM/AM2ARM/tree/v1.6.3-launcher-beta.1/dependencies/darkos-audio)

## What runs on each display route

| Component | Consumer and alternatives |
| --- | --- |
| Python 3.11, Tcl/Tk, X11, fonts, Python extension modules and their support libraries | The launcher uses Python for route selection and setup. Tk and its X11 libraries provide the offline installer. The xdelta3 executable checks and reconstructs the supplied game data. A firmware interpreter alone does not establish support for the same Tk, compression, hashing and foreign-function modules. The Wayland game script uses the firmware's Python. |
| `runtime/core/` and `runtime/lib/libstdc++.so.6`, `libgcc_s.so.1` | The launcher initially calls the paired Debian glibc 2.36 loader and Python to select a display route. Direct-display sessions use the firmware loader on the KNULLI and muOS Brick, the dArkOS G350 and supported AmberELEC profiles. Other direct profiles use the bundled loader. Earlier TrimUI Brick firmware rejected game imports of `GLIBCXX_3.4.29` and `GLIBCXX_3.4.30`. The paired GCC 12 libraries satisfy those imports. On the Wayland installer path the firmware loader runs the packaged Python/Xwayland with `runtime/lib`. The Wayland game's library path points into its edition directory. |
| Installer `runtime/bin/Xwayland` and `xkbcomp.bin` | An existing Wayland socket supplies the compositor. The installer starts a private X server with a cookie and TCP disabled. Its local patch requests a fullscreen 640×480 root window on the selected output. The game starts its own rootless Xwayland for input and focus. Substituting the system X server must preserve dimensions, placement, keyboard lookup, focus and exit cleanup. |
| `runtime/bin/Xvfb` | On recognized direct-display boards it provides a private X screen for Tk and the game input window. The direct installer copies its X framebuffer into a firmware SDL window. Hardware output and game rendering still use firmware SDL/EGL/GLES. A system Xvfb is a candidate where its XKB paths, fonts, access control and supported options are available. |
| Edition `runtime/graphics/libGL.so.1` | Both editions contain the AM2ARM Wayland GL4ES build. It maps desktop GL to the firmware's EGL/GLES and has custom output selection and shared-context support for the second display. It is added to the game child’s library path. A generic system libGL cannot supply those AM2ARM entry points. |
| `runtime/kms/libGL.so.1`, `libwayland-client.so.0` and `libwayland-egl.so.1` | The graphics adapter uses a firmware SDL KMSDRM window and EGL context on Smart Pro S and on the qualifying Miyoo Flip V2 profile. The two Debian Wayland client libraries are direct link dependencies even on this KMS path. `libwayland-egl` supplies the Wayland client window ABI. The EGL implementation and GPU driver come from the device. |
| Westonpack Crusty GLX and GL4ES GLXpass | The TrimUI Brick's direct game display uses this bundled pair with firmware SDL2, EGL and GLES. The KMS and Wayland game routes use their respective adapters. |
| Device audio | On the dArkOS G350 the launcher starts a local PulseAudio server using the firmware’s ALSA output. On the muOS Brick it connects to the firmware’s PipeWire PulseAudio service. |
| Native extensions | Both editions contain the evdev haptics extension and the in-game save-transfer extension. Dual Screen adds the lower-display bridge. A separate TrimUI motor bridge is used on Brick and Smart Pro for the built-in controller. The launcher verifies the known replacement and preserves the original game library before installing it. |

These components stay under the port or game directory. The direct launcher loads its selected graphics adapter only for the runner and locates the device's ARM64 SDL2, EGL and GLES libraries at runtime. The runner contains GameMaker's own input implementation. The package supplies no stand-alone SDL2, Mali, Mesa, GBM or EGL driver. The system also supplies route-specific libraries such as `libcurl.so.4`. A matching filename by itself does not establish ABI or display compatibility.

The 99 filenames in the launcher's `runtime/lib/` represent 61 distinct binaries. The remaining entries reproduce Debian library aliases as ordinary files for game cards.

## Westonpack libraries in the launcher

The launcher's `AM2ARM/runtime/graphics/` directory contains `libGL.so.1` (GL4ES GLXpass) and `libcrusty.so` (Crusty GLX). The Brick can use both offline from a fresh installation. The upstream Westonpack 0.2.7.1 image is 55,398,400 bytes with SHA-256 `0bccaeebc11296bb1fe4278c9677cb82965c5a04bcd63745fa09d78228bc1a93`. The launcher checks each library before use. The build records its original path, size, hash and required libraries in the [Westonpack inventory](westonpack.tsv). [Upstream runtime image](https://github.com/PortsMaster/PortMaster-New/releases/download/2025-07-24_0745/weston_pkg_0.2.squashfs) · [Westonpack GLX example](https://github.com/binarycounter/Westonpack/wiki/OpenGL-2-Example)

On a KNULLI Brick with a FUSE-mounted exFAT game volume, the Ports entry mounts `knulli-runtime.squashfs` read-only. It contains a second copy of the same launcher tools, including the two Westonpack libraries. Both copies use the hashes in the inventory. The original game ZIP, installed game, saves and logs stay on the writable card.

BinaryCounter contributed the ARM64 runtime image in Westonpack 0.2.7.1. Its Git blob is `92f9b3cd37dcb9bb43c37c0a4eee12d7d0b92e91`. The image in that commit and the image in the runtime release match byte for byte. The two entries listed above come from the GLXpass and Crusty GLX directories. [Author's contribution](https://github.com/PortsMaster/PortMaster-New/pull/1824) · [Exact image and commit](https://github.com/PortsMaster/PortMaster-New/commit/b0e8206422c0fe79bec9ad266387ee45a861b2eb)
